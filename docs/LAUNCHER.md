# SD launcher and flash layout

The resident menu is an ordinary RP2350 RISC-V image at flash offset zero. It validates a `.RPG` file, installs its payload in a separate slot, records the installation and reboots before handing the image to the ROM `rom_chain_image` API. There is no CH32 serial bootloader or CHG-format compatibility.

| Flash offset | Region |
|---|---|
| `0x000000–0x07FFFF` | Resident menu, 512 KiB reserved |
| `0x080000–0x3EFFFF` | One installed game/app, 3,604,480 bytes maximum |
| `0x3F0000–0x3F1FFF` | Two save sectors |
| `0x3F2000–0x3F3FFF` | Two installation metadata sectors |
| `0x3F4000–0x3FDFFF` | Unused reserve |
| `0x3FE000–0x3FFFFF` | Core tail reserve / EEPROM area |

Standalone builds start at zero and stop below `0x3F0000`. The launcher build stops below `0x080000`. Menu builds start at `0x10080000` in XIP and stop below `0x103F0000`. All use 4 MB flash and no FS.

## Package version 1

A 512-byte little-endian header precedes a payload padded with `0xFF` to 4096 bytes. Header fields are magic `RPGAME1\0`, version 1, family `0xE48BFF5A`, layout ID `0x52504703`, offset `0x80000`, payload size and CRC32, title (32 bytes), author (32), release (16), reserved bytes, and CRC32 over the first 508 header bytes. CRC32 is reflected IEEE, polynomial `0xEDB88320`.

Both the Python packager and firmware verify the linked SDK IMAGE_DEF: RP2350 RISC-V, entry point inside the slot, stack `0x20082000`, and a closed metadata block loop. This release accepts the layout generated by Arduino-Pico 6.2.0, not arbitrary ROM image layouts. The complete file is read and checked before the first flash write. CRCs detect corruption; they are not cryptographic signatures.

Version 1 does not contain a board identifier or configure GPIOs. PiZero onboard-SD packages and Pico 2 external-SD packages can have identical family/layout fields while using different hardware. Use the supplied 0.3.1 PiZero card tree with the supplied PiZero launcher; replace earlier external-SD packages. `sdcard/catalog.json` records the build board for review, but the launcher does not enforce that catalog.

The Arduino core's prebuilt OTA blob has absolute addresses for flash zero. `scripts/linker.py` discards it and the OTA partition trailer, placing the relocatable SDK CRT0 metadata first. Picotool receives an explicit RP2350 platform for relocated image memory checks. Release verification independently checks the metadata loop, UF2 family, flash addresses and package CRCs.

## Interrupted installs and return to menu

Metadata records have generation numbers and CRCs. Before changing the slot, a newer INSTALLING record is committed in the alternate sector. Only after every payload sector is programmed and verified is a newer VALID record committed. A valid INSTALLING record overrides older VALID metadata. If power disappears during an install, the menu boots normally and can install again; the previous game is not retained in a second image bank.

Flash writes only accept aligned sectors within the app/save/metadata range. The RP core's flash erase/program routines execute from SRAM, with interrupts disabled and Arduino-Pico's other-core coordination. Save sectors and the resident menu are outside the installer image range. Writes, metadata commits and saves have host interruption tests; their physical timing has not been exercised on a board.

Launching stores a watchdog scratch request and resets. Early in menu setup, before LCD/SD/audio initialization, the request is consumed, installed bytes are CRC checked, USB is disconnected/reset and IRQs disabled. ROM chaining gets a word-aligned 4096-byte work area and the slot address/size. SDK startup initializes the new program's memory/peripherals. A ROM error triggers a fresh reset and a menu error message. START held three seconds in a game resets normally, so the request-free boot shows the menu.

Reference: [Pico SDK ROM runtime documentation](https://www.raspberrypi.com/documentation/pico-sdk/runtime.html), `rom_chain_image`, and Arduino-Pico 6.2.0's SDK CRT0/runtime sources. Physical handoff, boot recovery and button-return testing remain pending.
